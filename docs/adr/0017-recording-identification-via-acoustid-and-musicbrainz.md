# Recording Identification enriches Managed Import through AcoustID and MusicBrainz

> Superseded in part by [ADR 0019](0019-tag-based-import-and-album-artwork.md): Recording Identification is removed; genre and album artwork are optional. Bit-preserving storage remains in force.

Managed Import identifies each uploaded file as a MusicBrainz Recording instead of trusting tags alone. Evidence is tried cheapest first: a recording MBID already in the tags (Vorbis `MUSICBRAINZ_TRACKID`, ID3 `UFID` owned by `http://musicbrainz.org`, MP4 `MusicBrainz Track Id`, all written by Picard) is fetched directly; otherwise a tagged ISRC (`ISRC`, ID3 `TSRC`) is resolved through the MusicBrainz ISRC lookup; only then does the Music Server fingerprint the staged file with `fpcalc` (Chromaprint), look the fingerprint up on AcoustID, and, when the best result reaches the configured score threshold (default 0.90, highest `sources` count breaks ties), fetch that Recording from the MusicBrainz web service. Tagged identifiers are stored on the Track even when no lookup runs, so a Recording Duplicate is detected offline and the ISRC is kept. Tags remain the baseline. Recording-level fields (Title, Artists, ISRC) are replaced by the MusicBrainz values; release-level fields (Album, Album Artists, Year, disc and track position, Genre) stay as tagged and may only be completed from the release whose title equals the tagged Album (falling back to the earliest official album release) when the tag is empty. Because the Strict Import Profile already requires every one of those fields except Year and the position totals, the strict inspection still runs on the tags first and today only Year is ever completed; totals are deliberately left alone so the album position check that passed at Import Preview cannot fail at commit. Should a required tag ever be relaxed, validation must move after the merge. The audio file is never rewritten and artwork is never fetched, which keeps ADR 0011's Bit-Preserving Storage guarantee intact. The Track stores the recording MBID, the AcoustID score, the metadata source and the list of fields MusicBrainz changed, and the Import Preview and Import History show them so the behaviour can be inspected per file.

Two Tracks whose Recording Identification resolved to the same recording MBID but whose content hashes differ are a Recording Duplicate: the same user decision set as a Possible Duplicate (replace, import separately, do not import) with a clearer message. Exact Duplicate keeps its hash-only meaning.

Recording Identification is a per-Import Batch choice made by a switch in the Import Music modal and stored on the batch. When the switch is off, or when `fpcalc` is missing, the service is unreachable, no confident match exists, or `RECORDING_IDENTIFICATION_ENABLED=false`, no fingerprint is computed and no outbound request is made; the file is imported from its tags exactly as before and the Preview names the reason. Each outbound request has a fixed timeout with no retry (10 seconds for AcoustID, 30 seconds for MusicBrainz, whose recording lookups take several seconds for a recording on dozens of releases; the lookup omits the media include for the same reason), a server-wide limiter keeps MusicBrainz at 1 request/s and AcoustID at 3 request/s, and fingerprint and recording responses are cached in the database indefinitely. `fpcalc` is a Server Dependency installed like ffmpeg (system package, `chromaprint` in the container image), reported with ffmpeg in the health response and Settings page, never bundled, and never linked through cgo. The AcoustID application key ships embedded and `ACOUSTID_API_KEY`, `ACOUSTID_BASE_URL`, `MUSICBRAINZ_BASE_URL` and `RECORDING_IDENTIFICATION_MIN_SCORE` override the defaults, following the Radio Browser precedent.

This is a deliberate exception to the project's rule against hosted third-party services: AcoustID and MusicBrainz are the only open, non-commercial databases that can name a recording from its audio, the feature is opt-out per batch and degrades silently to the tag path, and no operator needs an account.

## Considered Options

- Run MusicBrainz Picard headless: rejected because Picard is a Qt desktop application whose command-line mode still starts the GUI process, adding Python and Qt to every server installation.
- Make MusicBrainz the sole metadata source and treat tags as invalid: rejected because a self-hosted server must import offline, and release selection (single, standard, deluxe, regional pressings) would reshape the user's album layout on every import.
- Replace the Album identity key with the MusicBrainz release MBID: rejected because per-file release selection could split one album across regional releases; the metadata identity key stays authoritative.
- Bind libchromaprint through cgo or bundle `fpcalc` as an mpv-style sidecar: rejected because the server build is cgo-free and the sidecar pattern is a Desktop Client decision (ADR 0005), while ffmpeg already sets the system-dependency precedent.
- Advertise `fpcalc` availability as a dynamic Server Capability: rejected because Server Capabilities describe a release's behaviour for client compatibility (ADR 0006), not the deployment environment; a separate Server Dependency report carries that.
- Fingerprint through ffmpeg's `chromaprint` muxer instead of a separate `fpcalc`: rejected because the Alpine 3.21 `ffmpeg` package is built without that muxer, while its `chromaprint` package (1.5.1) ships `/usr/bin/fpcalc` and was verified to fingerprint an MP3 inside the image.
